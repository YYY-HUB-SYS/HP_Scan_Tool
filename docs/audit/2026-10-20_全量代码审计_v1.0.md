**位置**

**触发条件**
用户在 GUI 选择输出格式 PDF → 协调器把 `application/pdf` 发给打印机 → 打印机直出 PDF 字节 → 缓存文件 `page_001.pdf` 是**真 PDF**。之后保存阶段用 Pillow 打开它。

```
2) save_pages 源为 PDF  ->  saved_files = []   # 输出目录只剩源文件，一个成品都没有
```

### C-2　监听模式 / 手动探测 / 状态查询 / WIA 四条链路的 UI 回调全部失效

**位置**
- 监听模式：`hp_scan_gui_pyside.py:1583, 1607, 1610, 1630, 1633, 1635, 1637`（线程在 `:1639`）
- 手动添加打印机探测：`hp_scan_gui_pyside.py:1712, 1714, 1716, 1718`（线程在 `:1720`）
- 打印机状态查询：`hp_scan_gui_pyside.py:1761`（线程在 `:1763`）
- WIA 扫描：`hp_scan_gui_pyside.py:1857, 1860, 1862`（线程在 `:1864`）

**根因**
这些位置全部是"在 `threading.Thread` 里调 `QTimer.singleShot(0, lambda: ...)` 把 UI 更新投递回主线程"。但 **QTimer 的线程亲和性 = 创建它的线程**，工作线程没有事件循环，定时器永远不会被触发。

**实测（对照实验，排除方法学误判）**
```
主线程 singleShot(0, 命名函数)   触发: True
主线程 singleShot(50, lambda)    触发: True
主线程 QTimer 实例               触发: True
工作线程 singleShot(0, 命名函数)  触发: False      <-- 问题路径
工作线程 3 次 singleShot 触发数:  0
工作线程(自带 QEventLoop)        触发: True
工作线程 emit Qt 信号 -> 主线程槽 触发: True       <-- Qt 队列连接本身没问题
```
结论：问题不在 Qt 跨线程信号，而在**用 QTimer 代替信号做跨线程投递**。

**实际后果**
1. 监听模式扫描成功 → `hp_scan_gui_pyside.py:1607/1630` 的预览对话框**不弹出**；扫描数据已写进缓存，但用户永远看不到、也拿不到（缓存还会被 `cleanup_stale` 清掉）。
2. `hp_scan_gui_pyside.py:1637`（`finally: QTimer.singleShot(0, self._reset_scan_ui)`）不执行 → **扫描按钮永久停在"监听中..."禁用态，只能重启程序**。
3. 手动添加打印机的"探测"按钮（`:1718` 重新启用）永不执行 → 永久禁用；状态文字永不更新。
4. 打印机状态对话框（`:1761` → `_on_status_received`）永不弹出。
5. WIA 扫描的结果与错误提示（`:1857-1862`）全部不显示。

**同仓已有正确范式**
`hp_scan_gui_pyside.py:820-837`：工作线程写共享 dict，主线程用 200ms `QTimer` 轮询 —— 这是启动探测用的正确写法。四处坏代码没有沿用它。

**最小修复**
把这 4 处改成主窗口上的一个 `QObject` 信号（如 `ui_call = Signal(object)`），工作线程 `self.ui_call.emit(fn)`，主线程槽里执行；或统一复用 `:820-837` 的轮询范式。**不要**再用 `QTimer.singleShot` 做跨线程投递。

### I-1　发现流程超时后永久卡死：发现按钮此后完全失效

**位置**：`scan_coordinator.py:241`（`concurrent.futures.as_completed(futures, timeout=15)`）；`scan_coordinator.py:212-219` 的 `try` 只包住 `discover_all_scanners`，`as_completed` 在 try 之外；GUI 侧 `hp_scan_gui_pyside.py:1198` 的 `_discovering` 守卫。

**触发条件**：局域网内有多台打印机，其中某台探活（`probe_escl`）慢，15 秒内未全部完成。

**实际后果（实测）**
```
as_completed 超时 -> 抛出: TimeoutError 4 (of 4) futures unfinished
模拟 5 台慢设备调用 discover_scanners_background:
  on_complete 是否被调用: None    # 线程直接死掉，回调永不触发
```
`TimeoutError` 逃出 `_discover` 线程 → `on_complete` 永不调用 → GUI 的 `self._discovering` 永远停在 `True`（`hp_scan_gui_pyside.py:1201` 设置，只有 `:1208` 的回调会复位）→ **此后每次点"刷新"都在 `:1198` 被 `return` 掉，整个会话内发现功能永久失效，且界面无任何错误提示**（状态栏一直停在"正在发现扫描仪..."）。

**最小修复**：`scan_coordinator.py:241` 外包一层，把超时当正常结束处理：
```python
try:
    for future in concurrent.futures.as_completed(futures, timeout=15):
        ...
except concurrent.futures.TimeoutError:
```

### I-2　窗口关闭后进程被线程池挂起，最长可达扫描超时（ADF 300 秒）

**位置**：`scan_coordinator.py:406-413`（`shutdown()`：`self._pool.clear()` + `self._pool.waitForDone(3000)`）；GUI `hp_scan_gui_pyside.py:1941-1944`（`closeEvent` 里调 `coordinator.shutdown()`）；扫描超时 `scan_coordinator.py:356`（ADF `timeout=300.0`）。

**触发条件**：扫描进行中关闭窗口。

**实际后果（代码路径判定）**

### I-10　自动 A4 裁剪把缓存原件改写成 JPEG：扩展名与内容不符，且原始几何不可恢复

## 五、CI 与打包专项

### 5.1 `.github/workflows/build.yml` 的实际可运行性

| 项 | 结论 |
|---|---|
| 语法/结构 | **可运行**。`checkout@v4` → `setup-python@v5` → `pip install -r requirements.txt` → `pip install pyinstaller` → `python build_exe.py` → `upload-artifact@v4`，release job 用 `download-artifact@v4` + `softprops/action-gh-release@v1`，action 主版本互相匹配，无版本错配 |
| 触发条件 | push main / tag `v*` / PR main，**合理** |
| 产物 | `dist/HP_Scan_Tool.exe` 单文件，与 `build_exe.py:16,64` 一致 |
| **致命缺口** | **CI 从不运行测试**：整个 workflow 没有 pytest 步骤。`requirements.txt` 里也没有 pytest（7 行里无测试依赖）→ **`tests/` 下 1571 行测试在 CI 里一次都没跑过**，任何回归都能直接合进 main 并打出 exe |

**附带问题**
1. **Python 版本不一致**：CI 用 `python-version: '3.11'`（`build.yml:23`），而项目实际运行环境是 3.12.10（实测）→ CI 编出来的 exe 与本地验证环境不是同一个解释器。
2. **无打包后冒烟验证**：只 build 不跑，连"exe 能否启动"都没验证。考虑到 C-2/C-3 这类"运行期才炸"的问题，一个 `--version` 级别的冒烟就能挡住大部分。
3. **release job 在 ubuntu 上跑**：只是下载 Windows 产物再打包 release，功能上没问题，但没必要跨平台。

**最小修复**（`.github/workflows/build.yml`）
```yaml
      - name: Install test deps
        run: pip install pytest
      - name: Run tests
        run: python -m pytest tests/ -v
```
并把 `python-version` 改成 `'3.12'`。

### 5.2 `build_exe.py` 的 hidden-imports 覆盖度

已覆盖：`escl_engine` `wia_engine` `wsd_engine` `listen_engine` `scan_coordinator` `save_manager` `cache_manager` `history_manager` `profile_manager` `requests` `urllib3` `zeroconf` `PIL` `PIL.Image` `xml.etree.ElementTree`。

**缺口**
- `wsdiscovery` —— `wsd_engine.py:27` 的 `from wsdiscovery import WSDiscovery` 是**函数内 import**且**带 try/except ImportError**（`:28-30`）→ **即使打包漏了，运行时也只会静默返回空列表**，WSD 发现无声消失，没有任何报错。
- `win32com.client` —— `wia_engine.py:30,104` 同样是函数内 import 且被 `except Exception` 吞（`:32-34`）→ 漏打包则 WIA 静默不可用。
- `cli` —— CLI 未打进 exe（`build_exe.py:57` 只指定 GUI 入口），若期望 exe 也支持 `hp_scan.exe scan ...`，需另加入口。

**最小修复**：显式补 `--hidden-import wsdiscovery` 与 `--hidden-import win32com.client`，并在 `build_exe.py` 打包后加一步"检查产物内含这两个模块"的断言。

## 七、面向四个新功能的基础设施缺口

> 对应 `docs/design/2026-10-20_新功能调研与方案_双面_续扫_纠偏_曝光_v1.0.md`。以下每条都指明"缺口在哪、当前代码里能复用什么、要新造什么"。

### 7.1 多页 / 多批次任务的元数据模型：**不存在**

**现状**
`cache_manager.write_page(job_id, page_num, data, ext)`（`cache_manager.py:138-153`）只落**字节 + 扩展名**，文件名 `page_001.jpg`。没有 manifest、没有页元数据、没有任务元数据。`cache_manager.list_pages()`（`:164-183`）返回 `(page_num, ext, path)`，同样不含任何几何信息。

`job_id` 是 `datetime.now().strftime("%Y%m%d_%H%M%S_%f")`（`scan_coordinator.py:343`）—— 一串时间戳，**不含设备、参数、批次号、页数**，无法据此恢复"这批是哪台机器、什么参数、扫到第几页"。

> **2026-10-21 订正**：上面这行描述的 job_id 生成方式**已被本轮替换** ——
> 现在由新模块 `naming.py` 统一生成：`<秒级时间戳>_<1位字母+7位十六进制>`
> （如 `20261021_065432_a3f19a2c`，提交见「统一命名形态」那笔）。
> 原因：本机 Windows **系统时钟粒度只有 15.625 ms** ⇒ 同一 tick 内
> `strftime("%f")` **99.5% 相同** ⇒ 而 **job_id 就是缓存目录名**
> ⇒ 同一 tick 起的两次扫描会**共用一个目录、逐页覆盖**（丢的是扫描产物、零报错）。
> ★ 本审计 M-11 预言的「输出名会撞名」问题由此确认为**真实且更严重**
> （不只是输出名，job_id 也会撞）。
> 另：本节其余结论（元数据模型缺失等）仍成立，未随该订正变化。

**新功能会立刻撞上的点**
- **断点续扫**：需要知道"本次任务已取到 N 页、打印机侧 job_uri 是什么"→ 现在两者都无处存放。
- **分批合并**：需要知道"第几批、共几批"→ 只能靠文件名猜。
- **双面合并**：需要知道"这批是正面还是背面"→ 无处记录。

**需要新造**
1. `cache_manager` 增加 manifest：`{job_id}.json`，含任务元数据（device ip/model、resolution、color_mode、source、duplex、created_at、total_pages、batch_index）。
2. 每页一个 sidecar 或 manifest 里的页数组：`{page, file, width, height, format, rotation, skew_angle, crop_box, source_batch}`。
3. `write_page` 增加一个 `meta` 入参，或新增 `write_manifest` / `read_manifest` / `update_manifest`。

### 7.2 页面几何信息（尺寸 / 旋转 / 纠偏角）：**几乎全部没被保留**

| 信息 | 现状 | 位置 |
|---|---|---|
| 尺寸 | **不落盘**，只能靠 `Image.open` 现读 | `tools/verify_scan.py:126-131` 就是在干这件事（每次采集元数据都重新 open 全部页） |
| 旋转角 | 只存在于 GUI 对话框的**内存字典** `self._rotations`（`hp_scan_gui_pyside.py:2164`）→ 对话框一关就丢 | 无落盘 |
| 纠偏角 | **完全没有** —— 没有 deskew 实现，也没有任何地方计算过倾斜角 | — |
| 裁剪框 | `crop_to_a4`（`escl_engine.py:839-846`）只返回裁剪后的图，**不返回裁剪框**；`auto_crop`（`:771-836`）同理 | — |
| 原始几何 | **已被破坏** —— `_apply_a4_crop` 直接覆盖缓存原件（I-10） | `scan_coordinator.py:440-443` |

**结论**：**自动纠偏与断点续扫缺的不是算法，是元数据落地。** 建议在修 I-10 的同时把几何元数据一起落盘。

**能复用的**：`escl_engine.crop_to_a4` 与 `auto_crop` 都是纯函数，改成"返回 (图, 裁剪框/角度)"即可复用。

### 7.3 PDF 合并能力：**有"图片合成 PDF"，没有"PDF 合并"**

**现状**
- `save_manager.py:153` 的 `save_all=True, append_images=[...]` 是**把图片合成一个 PDF**，不是 PDF 级合并。
- 打印机直出 PDF 时整条路断（C-1）。
- 全量载入内存（I-11）。
- 多页 PDF 不做 A4 归一（I-13）。

**双面合并（odd/even interleave）需要的能力，现在一样都没有**
- 拆页（把一个 PDF 拆成单页 PDF）
- 页级重排（把第 2 批的页倒序后交错插入）
- 末页截断（背面比正面少一页时去掉末页）
- 跳过空白页（`is_blank_page` 存在但无调用方，可作为判据，但判定基于**图片**而非 PDF 页）

**建议**：`pypdf` 负责页级操作（merge/倒序/截断），Pillow 只负责"图片 → PDF 页"。同时把"打印机一律只出图片，PDF 全部本地合成"作为默认策略，可以一次性消掉 C-1 + I-11 + I-13。

### 7.4 图像处理的接入点：**没有处理链，每加一种处理就复制一遍改写逻辑**

**现状的三个接入点**
| 位置 | 行为 | 问题 |
|---|---|---|
| `escl_engine.auto_crop` / `crop_to_a4` / `is_blank_page` | 纯函数，可用 | `auto_crop` 慢（M-24）、`is_blank_page` 无人调用（M-27） |
| `hp_scan_gui_pyside.py:2106-2126`（`PreviewDialog._auto_crop`） | 读缓存 → 裁 → **写回缓存文件**（JPEG） | 覆盖原件、格式不保真、异常被吞成一行文字 |
| `hp_scan_gui_pyside.py:2323-2336` / `2338-2351`（多页 `_auto_crop` / `_auto_crop_all`） | 同样覆盖缓存文件 | `_auto_crop_all` 的 `except Exception: pass`（`:2348`）→ **全部裁边失败时用户零提示** |
| `scan_coordinator.py:431-445`（`_apply_a4_crop`） | 扫描后立刻裁，覆盖缓存 | 不可撤销（I-10） |

**曝光功能：ADR 已接受，实现完全不存在**
`docs/adr/0008-exposure-enhancement.md` 状态"已接受 (2026-07-16)"，定义了 `apply_exposure` 扩展参数（gamma / shadows / highlights / channel_gains）与 `presets.json`。**实测：全库 grep `apply_exposure` / `presets.json` / `brightness` / `contrast` 零命中** —— 既没有 `apply_exposure` 函数，也没有预设存储。设计文档 `:222` 提到"仓库 git 历史里的 `preset_manager.py`（154 行）"，说明它曾在历史中存在、被重构删除。

**建议的处理链模型**（能同时服务曝光/纠偏/裁边/旋转）
1. 缓存只存**原件**，任何处理都不覆盖它。
2. 每页维护一条**处理记录**：`[{op: "rotate", deg: 90}, {op: "a4_crop"}, {op: "deskew", angle: 1.2}, {op: "exposure", preset: "文字增强"}]`。
3. 预览与保存时按记录**重放**处理链 —— 这样"撤销上一次裁边"、"换一套曝光预设重新出图"都不需要重新扫描。
4. 曝光预设存 `presets.json`（与 `scan_config.json` 同级，符合 ADR-0008）。

### 7.5 断点续扫：**引擎层与缓存层都缺"会话"概念**

| 缺口 | 现状 |
|---|---|
| 打印机侧 job 复用 | `execute_multipage_scan` 每次都新建 job（`escl_engine.py:677-678`），**没有"接着上一次 job 取页"的能力**；`job_uri` 是局部变量，出函数即丢 |
| 已取页数记录 | 不落盘（7.1） |
| job TTL 窗口 | `escl_engine.py:549-551` 明确写着该型号 job 只能靠打印机侧 TTL 回收（实测 15-20 分钟）→ **续扫必须在 TTL 窗口内完成**，需要一个"续扫令牌"记录 job_uri + 过期时间 |
| 缓存生命周期 | 保存成功后 `remove_job` 整目录删（`save_manager.py:90-91`）→ 没有"会话级"缓存，续扫与分批合并都需要"会话未完成前不许删" |
| stale 清理 | `cleanup_stale` 不看 `_active_jobs`（M-18）→ **长任务期间缓存可能被误删**（设计文档 `:175` 已点名） |

### 7.6 跨批次 / 多任务的并发与命名

- 输出名秒级精度（M-11）→ 10 批必撞名 → **必须引入批次序号**（如 `HP_Scan_b03_20260101_120000`）或全局 job 序号。
  > **2026-10-21 订正**：M-11 **已修**，但方案**不同**：没有引入「批次序号」，
  > 而是由新模块 `naming.py` 统一生成 `<秒级时间戳>_<1位字母+7位十六进制>`
  > （**首字符固定字母** ⇒ 永远不会长得像 `_001` 组号）。
  > 原因：真正的问题是「把时钟当唯一键」—— 本机时钟粒度 15.625 ms，
  > **加到微秒也不够**（同 tick 内 99.5% 相同）⇒ 必须换一个**真正的唯一性来源**。
  > 另：本条还漏判了一点 —— **job_id 就是缓存目录名** ⇒ 撞名后果不止输出名被覆盖，
  > 而是两次扫描**共用一个缓存目录、逐页覆盖**（更严重）。
- 四个配置文件固定 `.tmp` 名 + 无跨进程锁（I-9）→ 分批任务若多进程并发写历史/配置会互相覆盖。
- `cache_manager` 的 `_lock` 是**进程内**锁，多进程无法互斥。
- `scan_coordinator` 的线程池 `setMaxThreadCount(4)`（`scan_coordinator.py:136`）允许 4 个扫描并发 → **4 个并发任务的输出名可能落在同一秒** → 覆盖。
