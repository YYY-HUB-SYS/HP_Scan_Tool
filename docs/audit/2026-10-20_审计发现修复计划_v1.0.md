### 批次 2 — PDF 路径重做（直接决定"400 页合并 PDF"能否成立）

**这一批同时解决 C-1 + I-11 + I-13，并铺好纠偏/双面/续扫的地基。**

#### 现状的根因：请求层与落盘层对格式的理解不一致

```
请求层：选 PDF → FORMAT_MIME["pdf"] = "application/pdf" → 打印机直出 PDF 字节
落盘层：save_manager 一律按图片处理 → Image.open(PDF 字节) → UnidentifiedImageError
        → 单页抛错；多页 except 吞掉 → saved_files=[] → 对话框静默关闭，0 文件产出
```

#### 决策：统一为「打印机只出图片，PDF 本地合成」

| | 方案 A（推荐） | 方案 B |
|---|---|---|
| 做法 | 选 PDF 时请求层也请求 `image/jpeg`；PDF 在本地合成 | 保留打印机直出 PDF；落盘层做 PDF→PDF 合并 |
| C-1（静默 0 文件） | 消失（不再有"PDF 字节当图片打开"） | 需专门处理 |
| I-13（单页/多页 PDF 尺寸不一致） | 消失（本地统一 A4 画布） | 仍需处理 |
| I-11（400 页 OOM） | 可流式解决 | 可流式解决 |
| 新依赖 | `pypdf`（纯 Python，流式合并） | `pypdf` |
| 代价 | 打印机不再直出 PDF（矢量文字丢失）；JPEG 有损 | 保留直出 PDF |

**选 A 的理由**：文档扫描场景 PDF 本就是图片页，300dpi JPEG 质量 95 的损失可忽略；而 A 一次性消掉三个问题，并让"选 PDF"与"选 JPG"走**同一条**代码路径——这对后续的分组保存、双面合并、续扫合并都是关键（现在两条路径行为不一致，正是 I-13 的来源）。

#### I-11 的流式解法（400 页 ≈ 10.4GB 内存）

PIL 的 `save_all=True, append_images=[...]` 会把**所有页一次性载入内存**。正确做法是**两阶段**：

```
阶段一（逐页，内存只占一页）：
    for each page:  Image.open(cache_page) → A4 画布归一 → 存成单页 PDF（临时文件）
阶段二（流式合并）：
    PdfWriter 逐页 append → 输出最终 PDF
```

依赖 `pypdf`（纯 Python、无编译）。

#### I-9：A4 裁剪不得覆盖原件（**这是纠偏功能的前置条件**）

现状：`_apply_a4_crop` **原地改写缓存文件**，导致
- 扩展名撒谎（`.png` 文件头变成 `ffd8ffe0`，实测）
- **原件不可恢复** ⇒ 纠偏角无法回溯重算（A4 画布归一后算出的角度是"归一后的角度"，不是"原稿角度"）

修正方向：**页元数据记参数，落盘时才应用**。这要求引入页元数据模型 —— 见下。

#### 页元数据模型（批次 2 顺带产出，新功能的共同地基）

每页需要持久化：

```python
@dataclass
class PageMeta:
    cache_path: str        # 原始扫描件路径（永不修改）
    width: int             # 原始像素宽
    height: int            # 原始像素高
    manual_rotation: int   # 用户手动旋转角（0/90/180/270）
    deskew_angle: float    # 自动纠偏角（°）
    a4_normalized: bool    # 是否已做 A4 画布归一
    crop_rect: tuple | None  # 自动裁边框
```

**当前代码的缺口**（审计确认）：旋转角只存在 GUI 内存的 `self._rotations`，尺寸不落盘，纠偏角根本没有。**没有这个模型，续扫 / 双面 / 纠偏 / 大批量合并全都无从谈起。**

## 2. 批次 1/2 的执行约束

- **每个 Critical 都要有回归用例**，且用例必须**能被变异测试杀掉**（把修复改坏，测试必须失败）——这是本轮审查积累出的硬要求
- **不许用 `except Exception: pass` 掩盖新问题**（审计发现这类吞异常是多个 Critical 的直接成因）
- **不许原地改写缓存原件**（I-9 的教训）
- 每批结束时跑全量测试 + 敏感信息扫描
- 全部完成后推 `origin`（内网 Gitea）；**不推 GitHub**

## 3. 优先级理由

审计给的"最该先修 3 条"与本计划一致，但排序理由补充如下：

1. **批次 0（CI 门禁）** —— 成本最低、收益最高。后面每批都在改生产代码，没有 CI 门禁等于裸奔。
2. **批次 2（PDF 路径）** —— 用户的核心目标（400 页合并 PDF）**当前根本走不通**：C-1 静默产出 0 文件、I-11 必然 OOM。而且它是纠偏/双面/续扫的共同地基。
3. **批次 1（其余 Critical）** —— C-2 会**锁死扫描按钮**（用户可见的最严重交互故障）、C-4 让缓存上限失效（长期磁盘风险）。
